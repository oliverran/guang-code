# dsh-ppc-library

[English](README.md) | 中文

按领域划分的经验库：早前任务在这个领域采纳的 harness、它们贡献的经验，以及在它们之上的词面检索。

本包是纯库。它在调用方拥有的根目录下写出一库文件，把它读回来，并给库里持有的经验按当前任务打分。它不注册 service，不挂 plugin。

## 为什么需要一个库

一轮 Propose–Probe–Compose 只改进一个任务的 harness。如果改进随这一轮一起死掉，它的价值就微乎其微：同一个领域的下一个任务遇到同样的情况，得到同样的错误行为。

库让这套方法变成**递归**而不只是迭代。采纳了 harness 的一轮把它存下来，同领域后来的任务在画自己的编辑之前先把它当例子读。学习在任务之间复利，而不是每次从头开始。

检索靠构造保证：一个领域的目录里只会有同领域的条目，所以一条经验不可能在它没被学到的领域里触发。

## 目录布局

```text
<root>/<domain>/
  INDEX.md                        the index a reader browses first
  harnesses/<taskId>/harness/     the full adopted harness tree
  harnesses/<taskId>/EXPERIENCE.md why it was adopted, and the lesson
```

整棵树都被带走，从不留摘要。想复用早前任务某个组件的 proposer 需要的就是那个组件本身，而它的摘要没法被复制进 harness。

`domainDir` 和 `slug` 会折叠分隔符，所以领域名和任务 id 永远不可能指向库外的路径。`domainDir('a/b')` 是 `a__b`，不是 `a/b`。

## 蒸馏

`runDistiller(ctx, options)` 在一轮已结束的记录上跑一个 agent，把它回复里的经验读出来。`distilMission(options)` 渲染 mission。

这个 session 刻意很窄。它是全新的，所以它不继承调用方对话的任何一轮，也不记得 selector 偏好哪个候选。它的**工作目录就是这一轮的记录**，所以它读的每个路径都是记录里的路径。而它的**写入能力是零**：一个能写的 distiller 也能改写它正在推理的证据，于是那条经验描述的就是一份从未存在过的记录。

mission 说了两件让蒸馏保持诚实的事：

- **被采纳的候选不是唯一的证据。** 选择是在藏起 harness 的情况下比较交付物的，所以这个选择说的是哪个产出物读起来最好，而不是哪个编辑起了作用。出现在被拒候选里的编辑，可能才是真正让行为变好的那个；而被采纳候选里的编辑，可能对它为什么被选中毫无贡献。蒸馏读的是 trajectory，不是判决。
- **判决可以是 `confounded`。** 当一个候选一次改了多个组件、而没有任何一次执行能隔离出其中一个时，记录展示的就是这个。一条只靠 confounded 对比支撑的经验是猜测，而库里的猜测会被之后每个任务当成事实来读。

失败、超时、用 `NO_ENTRY` 拒绝、或者写出一条缺了必需字段的记录的 distiller，产出的是**完全没有经验**。这是正确结果，不是需要绕开的失败：这一轮没教出任何能被存下的东西，而库里没有猜测，好过库里有一条猜测。

## 准入门控

`add(taskId, harness, details)` 只在经验带齐三个必需字段时才存下条目：

- **cue** —— 这条经验适用的**情势形状**，所以它能在另一件事上触发。不是这个任务的事实：是那个模式。
- **lesson** —— 要对 harness 执行的操作，写成可施加、可检查的形式，并点名它所针对的组件。
- **evidence** —— 这条经验所依据的执行对比：哪些运行、哪些时刻。
- **confidence** —— 记录对这条论断支持到什么程度，以及为什么。可选。

缺前三条中任何一条的经验**完全不写**。调用返回 `{ rejected }`，库保持原样。

这是 harness2 的 `has_experience` 规则，也是这套方法反 hallucination 的核心。没有证据的经验是猜测——而存进库里的猜测不再是猜测了：它会被该领域之后每一个任务当成关于这个领域的事实来读，并被复制进它们的 harness。所以一轮如果支撑不起一条经验，它贡献的就是**零**，这是正确结果，不是需要上报的失败。

门控在写入处强制执行，而不在读取处：写入是唯一能强制这条规则的地方，因为后来的读取只会找到写入允许存在的东西。

## 索引

`INDEX.md` 是派生的，不是手写的。`rebuildIndex()` 从磁盘上实际有的东西重新生成它，所以一个与目录不一致的索引只是过期索引，而不是第二份真相来源。每一行点名条目、它 harness 所带组件的一行普查，以及条目的 `cue`——cue 正是读者最先扫的部分，因为它是唯一说明这条经验是否适用的部分。

`inventory(surface, tree)` 就是那份普查。它数的是运行时真正读的东西——skills、scripts、hooks——以及 always-on 字符数，因为 always-on 文本是每次运行都要花掉 agent 输出预算的那部分。

## 检索

`retrieve(options)` 给每条经验的 `cue` 与任务文本打分，返回最好的若干条：

- 分数是两个 token 集合的 **Jaccard 重叠**：交集除以并集。
- 阈值是 `minScore`（默认 `0.12`），深度是 `topN`（默认 `3`）。
- 同分按任务 id 决胜，所以同一个库对同一个任务永远给出同样的答案。

打分器是词面的，这是刻意的选择。它可解释——读者能看到究竟哪些词匹配上了，并判断这个匹配是不是真的。它免费：没有模型调用、没有向量索引、没有网络。而在库的规模上它足够用了，因为检索真正要答对的问题是「这条经验是不是关于同一种情势」，而词面重合在语义模型值得那份延迟之前很久就回答了这个问题。

分数只算在 `cue` 上。`cue` 是情势的形状；`lesson` 又长又具体，算在它上面等于拿任务去匹配经验的措辞，而不是匹配它面对的情势。

`renderLessons(matches)` 把匹配渲染成后来那个任务拿到的文本。只渲染 `cue` 和 `lesson`：evidence 引用具体的 rollout 时刻，动辄几百字，为一个提示花掉这么多上下文太不划算。需要细节的读者自己去库里打开条目。

## Model Experience

### 后来那个任务拿到的经验

#### What the model sees

模型看到渲染后的经验：每条匹配一个括号里的 cue 和旁边的 lesson，标题说明它们是这个领域早前采纳过的 harness。它看不到 evidence、harness 树或采纳记录——那些是库里的文件，只有读者想要细节时才打开。渲染文本还说明这些经验不是给这个任务的指令，并且早前任务的组件对工作区的任何断言都要重新核实：在那里那是事实，在这里那是假设。

#### Token effect

注入的只是匹配上的那些经验，一个什么都匹配不到的任务就什么都不拿到。因此代价与「库对**这个**任务有多少话可说」成正比，而不是与库的大小成正比：存了五十个条目的领域和存了五个的领域代价一样，只要只有一条会触发。

#### KV Cache effect

渲染出来的文本随任务变化，所以它不是稳定前缀，没法像 always-on section 那样在多轮之间共享。同一个任务的两轮会渲染出同样的经验，可以共享那段文本；不同任务的两轮不会，而 prompt section 自身的顺序保证了请求的其余部分保持稳定。

## Known Limitations and Deferred Work

- 打分器是词面的，所以一条用任务没有使用的措辞写成的经验不会触发。任务说「下载老是失败」而 cue 说「when a fetch times out」，两者没有任何共同词，于是经验检索不到。
- 一条经验只存放在一个领域里。一条本该对两个领域都适用的经验只存在其中一个，另一个领域的任务永远看不到它。
- 没有重新打分，也没有衰减。一次就正确的经验永远留在库里，而这里没有任何东西去度量它是否仍然正确。
- 库没有合并也没有淘汰。条目不断累积，浏览一个大索引的读者会看到这个领域的每一个条目，不管它匹配得好不好。
- 经验由解析模型回复的调用方写进来。本包不检查这条经验是否为真，只检查它完整到足以被存下。
